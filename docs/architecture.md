# Architecture

## Dependency direction

```text
core (pi-agent-core)  -> ai (pi-agent-ai) <- vertx (pi-agent-vertx)
```

The three Maven modules correspond to real publication boundaries:

- `ai` publishes `pi-agent-ai` and contains framework-neutral model, message, tool, cancellation, and streaming contracts.
- `core` publishes `pi-agent-core`, implements the stateful runtime, Agent Skills discovery, and native Java extension host, and depends only on the API plus validation libraries.
- `vertx` publishes `pi-agent-vertx` and contains the Vert.x/Mutiny transport, SSE and Smithy event-stream framing, and all provider implementations.

Published artifacts use Maven group `io.github.idoly`; Java packages use `io.github.idoly.pi.*`.

Deterministic scripted streams are Core test fixtures, not a separately published module. Provider codecs stay in `vertx` until another transport implementation or independent release lifecycle makes a further split useful.

Agent Skills remain resource data, not executable extension classes. `SkillRegistry` discovers global, trusted-project, package, and explicit roots in deterministic first-wins order, parses frontmatter with SnakeYAML's safe constructor, preserves full instructions for on-demand disclosure, and bounds each root to 32 levels, 10,000 filesystem entries, and 2 MiB per skill. Project trust gates default project roots; package and explicit roots are host-authorized inputs.

Native Java extensions are loaded through `ServiceLoader` in an isolated `URLClassLoader`. Initialization and active hooks run in deterministic extension order; shutdown runs in reverse order. Session lifecycle calls are idempotent, and reload closes the old runtime and classloader before discovering the replacement. Resource discovery can contribute Skill roots; input, session transition, compaction, and model-change APIs are explicit host orchestration points. Durable extension state appends namespaced custom session entries, so it does not introduce a second persistence authority. The SPI is headless: the embedding host owns project trust decisions, command dispatch, and session replacement orchestration, while renderer, editor, theme, overlay, and TypeScript loading surfaces stay outside the SDK.

Provider middleware crosses the Core/transport boundary through `ProviderRequestHooks`. Headers use immutable JDK maps, request payloads use a JSON-compatible JDK object tree, and responses expose status plus multi-value headers. Vert.x converts that tree through Jackson only inside the transport module. Header and payload hooks are awaited before serialization/send; response hooks are awaited before SSE or Smithy event-stream consumption; non-2xx transport failures notify the hook before the original structured HTTP exception is rethrown. Bedrock applies hooks before SigV4 and regenerates reserved signing headers afterward.

The Core consumes a `ModelStream`, represented as a JDK `Flow.Publisher<AssistantStreamEvent>`. Mutiny `Multi` implements `Flow.Publisher`, so this boundary needs no reactive-streams adapter. Vert.x, Mutiny, Netty buffers, and event-loop types do not enter the Core API.

## Runtime baseline

- JDK 25 compilation and runtime
- Vert.x 5.1.6
- SmallRye Mutiny 3.3.0

Vert.x owns HTTP connection pooling, HTTP/2 multiplexing, TLS, request timeout, and stream reset. Mutiny owns asynchronous composition, single-subscriber buffering, demand, idle timeout, and cancellation propagation. Transport parsing covers SSE and CRC-validated AWS Smithy event-stream frames; public binary chunks use defensively copied `byte[]`, including binary/UUID event headers, so Vert.x `Buffer` remains module-local.

## Concurrency contract

One Agent accepts one active run. Its lifecycle events are serialized and listeners are awaited in registration order. Different Agent instances can execute concurrently.

A tool batch is preflighted in assistant source order. Parallel tools then execute concurrently. Completion events retain actual completion order, while persisted `ToolResultMessage` instances retain assistant source order. A sequential tool forces its complete batch to execute serially.

Provider and tool cancellation uses `CancellationSignal`. The Vert.x adapter maps cancellation to HTTP/2 stream reset or HTTP/1.1 request cancellation without blocking an event-loop thread. For JSONL sessions, a committed abort additionally publishes a stable per-generation/lane/run advisory marker beside the operation lock. Active effect registrations observe that marker on a virtual thread and trigger the same cancellation path across JVMs. `JsonlOperationAbortNotifier` is an optional injected pub/sub transport keyed by normalized generation path, lane, and run ID, with the committed abort sequence in each notification. Legacy observers retain the `Runnable` callback and verify the exact lane/run against the durable log; implementations of the compatible `JsonlOperationAbortNotifier.Sequenced` subinterface deliver the full notification so verification targets the committed sequence and rejects mismatched keys or non-abort mutations without changing the base SPI. Deployments choose `MarkerObservationMode.POLLING` (the compatibility default), `WATCH_SERVICE`, or `DISABLED` through the full repository constructor, and may run an external notifier alongside any mode. WatchService observation checks marker existence before registration and immediately after directory registration, then listens for create/modify/overflow events. Unsupported registration, invalid watch keys, or I/O failure fall back to polling; interruption during subscription close exits without fallback. The Linux/inotify path is verified both between independent handles and between independent JVMs: a parent marker commit wakes a child Provider owner, which cancels, reconciles the abort-only suffix, and publishes terminal `ABORTED` without polling or external pub/sub. The JSONL marker is still published in every mode for diagnostics and fallback recovery. `DISABLED` suppresses background observation but retains a one-time registration fence after external subscribe, so an abort committed before subscription is recovered from the marker without starting a polling thread. Neither marker existence nor external delivery is trusted by itself: both paths acquire the generation writer lease and confirm a matching durable `AbortRequested` record for the exact lane/run before invoking cancellation. A forged or stale marker leaves WatchService active for a later modify event; polling samples at its normal interval but performs durable verification only when the marker's mtime, size, or payload changes, avoiding repeated writer-lease acquisition and full-log reads for one unchanged rejected artifact. Marker payloads are bounded to 32 bytes and must encode one canonical positive sequence; verification accepts only an exact lane/run `AbortRequested` at that sequence and stops once the ordered log passes it. Oversized, malformed, non-abort, and wrong-operation sequence references are rejected before cancellation. A forged external notification is ignored. `markerObservationDiagnostics()` returns repository-instance, process-local monotonic counters for WatchService starts and fallbacks, polling starts, and durable advisory accept/reject decisions. They expose platform fallback behavior without entering recovery authority or the durable log. External observe, publish, callback, and subscription-close failures are passive. Notification occurs after the writer lease releases, so a synchronous subscriber can reconcile without lock inversion. Every registered cancellation has a one-shot gate across local abort, marker, external transport, and register-after-abort races. All callbacks for one loaded `(lane, runId)` share a single persistence-level marker/external subscription, which fans out through the state registry; registration close removes only that callback and operation-claim release closes the shared subscription exactly once. A parallel batch therefore avoids one polling thread or pub/sub subscription per tool while retaining one independent one-shot cancellation callback per effect. Marker or external notification is never durability authority: publication failure cannot invalidate an already committed abort, and settlement still checks the record log.

## Transport contract

The `vertx` module currently provides:

- pooled HTTP/1.1 and HTTP/2 connections;
- TLS and ALPN through Vert.x, covered by concurrent HTTP/2 multiplexing tests;
- incremental UTF-8 SSE parsing across arbitrary buffer fragmentation;
- Mutiny `Uni` response setup and `Multi` event delivery;
- bounded buffering before the stream subscriber is attached;
- request and SSE idle timeout propagation;
- cancellation and non-2xx response propagation;
- per-request provider headers;
- no blocking work on Vert.x event-loop threads.

Two OpenAI-family protocols live in `vertx`. `OpenAiModelStream` routes both over one shared Vert.x transport and pool:

- OpenAI-compatible Chat Completions serializes messages, images, tools, and tool results and maps text, structured reasoning signatures, indexed tool-call deltas, cache-aware usage, response metadata, provider errors, finish reasons, and `[DONE]`.
- OpenAI Responses serializes stateless input items and maps output text, reasoning, function calls, tool-result images, usage, completed/incomplete/error states, encrypted reasoning replay, and session cache affinity.

`VertxModelProviders` adds native Anthropic Messages, Google AI Studio/Vertex generateContent, Mistral Conversations, and AWS Bedrock ConverseStream routing over the same pool. Anthropic preserves thinking signatures and incremental tool JSON, groups consecutive tool results, and places default ephemeral cache breakpoints on the final tool and final user block; Google preserves thought signatures on text, thinking, and function calls; Mistral normalizes nine-character tool IDs and native thinking chunks; Bedrock uses bearer or SigV4 authentication and CRC-validates Smithy event-stream frames. `ProviderModelCatalog` contains 276 generated `0.84.2` models with pricing tiers. Runtime custom providers are parsed from structured `models.json` configuration and routed by API identifier.

Provider-specific wire behavior is explicit in `OpenAiCompatibility` and `OpenAiResponsesCompatibility`. These immutable profiles control roles, token fields, reasoning formats, strict-tool support, session-affinity headers, and tool-call ID normalization without adding provider details to the Core `ModelStream` contract. Chat reasoning profiles cover standard OpenAI, Qwen, Qwen chat-template, zAI, DeepSeek, OpenRouter, Together, and string-thinking request formats.

`Model.thinkingLevelMap` represents model-specific level support separately from provider profiles. A missing mapping uses provider defaults, a null value marks a level unsupported, and a string supplies the provider wire value. Clamping follows upstream pi's ordered-level behavior. `OpenAiModelCatalog` loads a versioned bundled snapshot generated from `@earendil-works/pi-ai 0.84.2`; it indexes only APIs implemented by this transport and pairs each framework-neutral `Model` with transport-owned compatibility metadata. `OpenAiModelStream` resolves that profile per model while explicit constructor profiles remain global overrides. Azure entries can be copied with a deployment endpoint through `Entry.withBaseUrl` without losing catalog identity.

`ToolDefinition.constrainedSampling` remains provider-neutral; the OpenAI codecs implement preferred or required strict JSON Schema sampling and share one strict-subset converter. Grammar constraints select Lark before regex, infer one required string argument property, use OpenAI custom-tool wire objects, and convert streamed raw input into append-only JSON tool-call deltas for the Core contract.

Agent execution maintains separate public transcript and run-local provider context views. `prepareNextTurn` may replace the latter, including system prompt, messages, and tools, without rewriting the event-derived public transcript. Model and thinking updates apply before the next provider request.

`AgentLoop` exposes the same runtime as a stateless invocation facade. `run` accepts an ordered prompt batch, while `continueRun` starts from existing user or tool-result context. `AgentLoopRun` is a single-subscriber `Flow.Publisher<AgentEvent>` with late-subscription buffering, demand accounting, cancellation, and a separate `CompletionStage` containing only messages created by that invocation. Steering is polled before the first provider request and after each completed turn; follow-ups are polled only when automatic tool continuation has settled. A tool termination hint suppresses automatic continuation but does not skip follow-up polling.

The Harness storage layer lives under `io.github.idoly.pi.agent.session`. `InMemorySessionRepository` owns versioned session discovery and lifecycle; each `AgentSession` is a lane-bound view over one shared immutable entry tree. Entries, operation records, and usage rows share one ID namespace and one mutation sequence across lanes and facts. Branch and record queries implement exclusive cursors and deterministic ordering; operation records additionally support lane, run, kind, and type filters. A per-lane open-operation index enforces at most one unfinished operation and is released by the matching finish record. Forks preserve selected entry IDs and facts while creating idle lanes with no record history or usage ledger. The separate `copyRetained` administrative extension accepts an exact set of source mutation sequences, preserves their source order, renumbers both outer mutations and embedded entries/records consecutively, and validates the complete replay before publishing a destination. It does not infer parent, lane, label, usage-entry, or operation-record dependencies: a retained set must be replay-closed, and any unknown sequence or broken dependency fails without creating the destination. Context projection starts at the latest compaction checkpoint, materializes its retained tail, and derives model, thinking, and active-tool state from the complete branch. Custom durable payloads use validated `JsonNode` values; pending assistant messages and unregistered application message classes are rejected before sequence allocation.

`io.github.idoly.pi.agent.harness.AgentHarness` intentionally matches the public 0.84.2 scaffold. It exposes defensive runtime configuration and rejects restore when any durable record exists. Prompting, queues, compaction, navigation, resume, watches, and hooks fail explicitly with `HarnessNotImplemented`; after close they fail with `HarnessClosed`. The upstream 0.84.2 package does not yet implement the durable interpreter described by its design document, so Java does not present speculative execution behavior as compatibility.

`JsonlSessionRepository` implements the published record-based JSONL v4 format. A header line is followed by one entry, record, lane, or fact mutation per physical line. Writes validate and encode a complete mutation before appending it, then publish the same mutation to the in-memory query state; an append failure leaves sequence, tree, and lane state unchanged. Open replays the shared sequence and all tree invariants. A syntactically incomplete final line is unacknowledged and is removed by writing the valid prefix to a sibling temporary file followed by atomic rename. A valid final line missing only its newline is repaired in place. Complete invalid lines and malformed interior lines are corruption and are never modified. Forks similarly stage a complete header plus logical entry/lane/fact snapshot and publish it by rename; operation records and usage are intentionally excluded. Because the common `SessionMetadata` contract has no cwd/path fields, one Java repository instance binds one cwd and enforces session IDs globally within its root.

JSONL mutation ownership uses a stable sibling lock file and an OS `FileLock`, with an in-process lock preventing overlapping-channel failures between repository instances in one JVM. Every append and staged transaction acquires that commit-scoped lease, reads only the final physical line (expanding the tail window for unusually large mutations), and requires disk sequence to equal the writer's expected predecessor. Two snapshots may remain open concurrently, but once one commits the other is fenced as stale and must reopen; it cannot append a duplicate sequence. Transaction batches verify their own consecutive sequence before copying and hold the lease through atomic replacement. Load holds the same lease while replaying or repairing a tail. Stable session-id leases serialize cross-process create, fork destination publication, and delete, preventing duplicate files for one id even when repositories use different timestamps. A repeated delete/recreate stress launches a fresh child JVM against each current generation, deletes and recreates the same session ID four times, and proves every stale child is fenced, all five generation paths are unique, discovery exposes only the latest file, and every historical generation lock tombstone remains. Lock files are outside discovery and contain no session data. Tests launch a separate JVM to prove that the OS lease blocks a parent-process commit and that a snapshot opened in the child is fenced after the parent advances the durable sequence; same-process locking is not treated as evidence for the cross-process contract.

Each repository `create` or `open` returns an `AgentSession` handle with a process-local lifecycle gate shared by all `view(lane)` objects created from it. `close()` is idempotent and rejects subsequent reads, writes, transactions, inspection, and operation dispatch with `SessionError.Code.CLOSED`; it neither deletes data nor closes independently opened handles over the same state. A fresh repository `open` returns a usable handle. Closing during an asynchronous structural effect prevents later settlement through that handle, releases its process-local execution claim through an internal cleanup path, and leaves the accepted durable operation recoverable after reopen. This models storage-handle ownership without adding persistent close state or holding JSONL leases for the handle lifetime.

JSONL create, retained copy, and fork publication use a sibling staging file under both the destination session-ID lease and destination writer lease. The staged header and all selected v4 mutations are forced before an atomic move; no non-atomic fallback is used for administrative publication. Retained copies snapshot the source under its normal load lease, validate and resequence in memory, preserve source timestamps, IDs, payloads, and parent links, and publish new destination metadata and mutation sequences. This operation is a Java session-level extension and does not alter the upstream-compatible fork contract, which intentionally excludes records and usage.

Persistent per-path lock files also act as generation tombstones. Destination allocation never reuses a filename for which either final data or a lock file already exists, even when the same session ID is deleted and recreated at the same clock millisecond. An old in-memory handle therefore remains bound to the deleted generation's absent path and fails with `STORAGE`; it cannot pass sequence fencing against a newly created session that happens to have the same ID, metadata timestamp, and sequence. Independent-JVM tests cover stale generation writes and same-ID create, fork, and retained-copy destination races. Each race permits exactly one publication; the loser observes `ALREADY_EXISTS`, and the final destination remains a single replayable JSONL file.

`JsonlSessionRepository.cleanupOrphanedStaging` is an explicit maintenance operation for crash leftovers. It recognizes only fixed repair/fork siblings (`*.jsonl.tmp`) and transaction files emitted by `createTempFile` (`*.jsonl<digits>.txn.tmp`). Every candidate is mapped back to its target JSONL path and deleted only while holding that target's writer lease, so cleanup waits for repair, fork publication, or transaction commit in another JVM. `StagingCleanupPolicy.minimumAge` optionally applies a retention period; modification time is read again after lease acquisition, so a file refreshed while cleanup was waiting is retained. Unknown `.tmp` files, malformed transaction names, final JSONL files, and `.lock` files are never removed. Lock files intentionally persist: unlinking a lock inode while another process is waiting on it can split future writers across different inodes and destroy mutual exclusion. Effect execution uses a separate per-session-generation/lane/run operation lock under `<session>.jsonl.operations/`; it does not hold the JSONL writer lock while a Provider or tool is running. A process that waits for an operation lock verifies its expected in-memory sequence against the disk tail immediately after acquisition. If the previous owner wrote an attempt, result, abort, or finish, the waiter is stale-fenced before dispatch and must reopen. If the previous process died without advancing the log, a SAFE effect may proceed under the newly acquired lease. Independent-JVM tests cover both assistant Provider and already-started tool effects. Forced child-JVM termination additionally proves three recovery branches: an unknown assistant effect leaves its durable attempt and therefore requires reopen plus a later-numbered attempt; an already-started SAFE tool whose log did not advance can be taken over by the waiting snapshot; and an initially dispatched NEVER tool remains suspended after reopen until `resolveNever` publishes operator-observed output. A remote abort can advance JSONL while the effect owner holds only the operation lease. Before terminal publication, the owner may reconcile a strictly consecutive suffix only when every added mutation is an `AbortRequested` record for its exact lane/run. It then follows normal abort arbitration and commits `OperationFinished(ABORTED)`. Any entry, usage, attempt, fact, queue record, other run, or other lane in that suffix remains a stale-writer error requiring reopen. Independent-JVM tests verify active Provider cancellation, single and parallel tool cancellation, abort-only reconciliation, source-ordered parallel error-result publication, and terminal recovery. Signal and lock paths include the immutable generation filename; delete/recreate allocates a new generation, so an old marker cannot cancel a replacement run even if session and run IDs are reused. Maintenance retains the old marker as an unassociated diagnostic artifact.

`inspectMaintenance` provides a read-only artifact snapshot for operator policy. It reports final sessions, recognized staging files, per-session writer locks, session-ID locks, operation-execution locks, and operation-abort signal markers with absolute paths, size, modification time, associated target/session ID, and whether corresponding final or staging data was visible during the scan. `MaintenanceQuery` can filter kinds and bound returned details while `MaintenanceReport.count` still reports complete repository-wide counts for every kind plus matched/truncated metadata. Inspection uses a first pass containing only final/staging association indexes and a second streaming pass; bounded queries retain at most `limit` artifact details in a heap, so large populations of persistent lock files do not produce an equally large result allocation. Malformed final sessions remain visible even when their header cannot provide an ID. The maintenance report neither acquires/probes writer locks nor deletes files, so it does not block active commits. `associatedDataPresent=false` is diagnostic only: an active create may hold its ID lease before publishing any data, and the report cannot establish that a lock is unheld. Lock deletion remains deliberately outside the repository API. `cleanupUnassociatedOperationSignals` is a separate retention-aware administrative path for strictly recognized `<64 lowercase hex>.abort` markers only. For each candidate it acquires the corresponding operation lease first and generation writer lease second, then re-reads marker attributes and target existence. Associated final generations and markers newer than `minimumAge` are retained. Old unassociated markers are deleted, while operation, generation, and session-ID lock files always remain. Acquiring operation before generation follows effect settlement lock order and ensures cleanup waits for active local or remote owners; an independent-JVM test proves the marker remains until the owner releases its OS lock. Re-reading mtime after both leases prevents deleting a signal refreshed while cleanup waited. Unknown/malformed `.abort` names are ignored rather than interpreted.

`inspectRecovery` is the complementary record-level repository scan. It visits each final generation under the normal JSONL load lease, strictly replays and validates it without repairing a torn tail or adding a missing newline, and runs `SessionOperationInspector` for healthy sessions. `RecoveryReport` keeps complete counts for scanned generations, open operations, corrupt sessions, unresolved SAFE effects, and unresolved NEVER effects while retaining only `RecoveryQuery.limit` details in a heap. Kind filters affect returned details and `matched`, not complete counts. An optional `ToolRecovery` filter can isolate operations containing `ADMINISTRATIVE_RESULT_REQUIRED` or `REPLAY_ALLOWED` effects. Corrupt generations become `RecoveryFailure` details and do not suppress diagnostics from healthy sessions. The scan does not probe or wait for operation-execution locks and never dispatches effects; it does acquire each commit-scoped writer/load lease so the generation is stable while being decoded. Detail memory is bounded by the query limit, while replay memory remains bounded by the largest individual session being inspected. Recovery details have a stable lexicographic key of normalized generation path, detail kind, and lane. `RecoveryQuery.after` resumes strictly after a `RecoveryCursor`; when a bounded page is truncated, `RecoveryReport.nextCursor` identifies its last retained detail. Every page rescans the repository and repeats complete repository-wide counts, while `matched` counts filtered details after that page's cursor. A missing `nextCursor` means the current scan has no later matching detail. Cursors are best-effort continuation rather than snapshot isolation: generations added, removed, or renamed between pages can change later results, but each page still retains at most its limit.

`createRecoveryCheckpoint` publishes a durable versioned JSON inventory outside the sessions root through a forced staging file and atomic move. Each discovered final generation is fingerprinted while holding its own writer lease, recording repository-relative path, parseable session ID, parseable tail sequence, byte size, and SHA-256. Malformed generations remain represented with null identity or sequence rather than being skipped. The checkpoint manifest is immutable input to `verifyRecoveryCheckpoint`, which re-fingerprints expected paths and scans for additions, returning complete `UNCHANGED`, `CHANGED`, `MISSING`, and `ADDED` counts with limit-bounded drift details. Verification never repairs session data or modifies the manifest. `verifyRecoveryCheckpoint(checkpoint, limit)` remains the simple bounded API; `verifyRecoveryCheckpointPage(checkpoint, RecoveryCheckpointQuery)` adds a cursor without a null-overload ambiguity. Drift ordering is relative path then status. `RecoveryCheckpointCursor` resumes strictly after that key, and a truncated page returns its last retained drift as `nextCursor`; every page recomputes and repeats complete status counts while `matched` counts drift after the cursor. `verifyRecoveryCheckpointBatch` adds an independent fingerprint budget over the ordered union of expected and currently added generation paths. `RecoveryCheckpointScanQuery` limits `maxGenerations`, optionally checks a non-negative duration between fingerprints, and resumes after a `RecoveryCheckpointScanCursor`; zero duration still verifies one candidate. `RecoveryCheckpointBatchReport` returns batch-only status counts, inspected count, and a next scan cursor when more union candidates remain. Its nested `RecoveryCheckpointQuery` independently limits drift details within the batch, so callers exhaust detail pages before advancing the fingerprint cursor. `RecoveryCheckpointVerifier` performs that orchestration and reports immutable progress state containing both cursors, cumulative counts, inspected generations, current-batch accounting, and an explicit terminal bit. Resuming a completed state is a no-op. Progress state is emitted after detail delivery, so external detail effects are at-least-once unless the consumer atomically persists its effect and state or uses a stable idempotency key. Paths are normalized and traversal outside the recorded repository root is rejected. Independent-JVM stress captures checkpoints while another process appends, deletes, and creates across multiple rounds; every manifest remains readable with unique paths and the race is represented only through the four documented statuses. This is deliberately per-generation consistency, not a globally simultaneous repository snapshot: discovery and individual leases occur over time, so concurrent create/delete can appear as later additions or omissions. A true point-in-time repository audit would require every writer to participate in a new global barrier, with explicit throughput and public protocol consequences.

`inspectRecoveryBatch` adds a separate generation scan budget. `RecoveryScanQuery` selects paths strictly after a normalized `RecoveryScanCursor`, retains the lexicographically smallest `maxSessions` candidates in an O(maxSessions) heap while walking filenames, and opens only those generations. An optional non-negative `maxDuration` is checked between replays; even a zero duration inspects one generation so the cursor always advances. `RecoveryBatchReport.nextScanCursor` is the last inspected generation when more eligible paths remain, and `scanComplete=true` requires a null cursor. Counts inside a batch describe only generations replayed by that batch, unlike unlimited `inspectRecovery` counts. The nested `RecoveryQuery` still independently limits and filters details from those generations; if its detail report is truncated, callers page those details before advancing the generation cursor. Batching bounds expensive session replay count/time and detail retention, while directory-name traversal still covers the repository to choose a stable next path.

`SessionRunOperation` is a Java session-level extension layered beside the published Harness scaffold. It atomically accepts `operation_started` plus provisioned prompt entries, writes an `ASSISTANT` attempt with a reserved result ID before model dispatch, and atomically publishes each assistant entry and usage. A terminal assistant publishes finish in the same transaction. For a tool-calling assistant, the operation remains open and returns `ToolsPending`. Tool-enabled model turns run through an internal terminate-blocker: Agent argument preparation and event reduction still apply, but no real tool effect crosses the durable boundary and synthetic blocked results are discarded.

`SessionToolExecution` consumes a persisted tool-calling assistant in source order. Every invocation, including deterministic unknown/invalid failures, receives a durable `tool_started` record and reserved result ID before execution; actual tools default to `Replay.NEVER`, while callers must explicitly opt a tool into `SAFE`. Sequential mode publishes each result entry and optional usage in one transaction. Parallel mode atomically writes every start before dispatch, allows effects to settle concurrently, then atomically publishes all result entries and usage in assistant source order. `SessionToolExecutionEvent` exposes durable-before-effect starts, real completion-order finishes, and durable source-order result publication; listener failures are passive. A tool whose own execution mode is sequential forces sequential dispatch. Recovery skips an existing source-ordered result prefix, replays a missing SAFE effect, and returns `Suspended` without dispatching a missing NEVER effect. Calling `execute` when starts already exist is rejected so callers cannot bypass replay arbitration by using the wrong entry point. `resolveNever` is the explicit no-replay administrative path: it accepts only a missing NEVER invocation, validates the source-order result prefix under the operation lease, and publishes an operator-supplied result plus optional usage to the already reserved ID. SAFE, duplicate, missing, and out-of-order resolutions are rejected. `BeforeToolCall` runs only after its durable start exists; a blocked decision becomes a durable error result and may set the entry's native `terminate` flag without executing the tool. `AfterToolCall` patches content, details, usage, error, and terminate before the result transaction. Hooks are part of the same unknown-effect envelope as the tool: SAFE recovery may repeat them, while NEVER recovery suspends before repeating any unknown hook/tool/after state. A run terminates after a tool batch only when every durable result entry has `terminate=true`, matching Agent batch semantics.

Run recovery validates the v4 record log, reconstructs the system prompt from durable intent and the effect-start leaf from mutation sequence, uses a later-numbered attempt only for an unknown assistant effect, honors durable abort before dispatch and before assistant publication, and enforces the process-local execution claim. Once all tool results exist, the next assistant turn starts again at attempt 1; incomplete results return the same `ToolsPending` state without model dispatch. A moved unknown-effect leaf is corruption rather than a new implicit context.

`SessionRunQueue` projects STEER, FOLLOW_UP, and NEXT_RUN state from existing `queue_enqueued` and `queue_cancelled` records; target entry existence is the consumed marker. Enqueue reserves the exact target draft ID, cancellation is idempotent, and drain publishes selected targets in one transaction and enqueue-sequence order. New assistant turns drain STEER before writing their attempt, but unknown-effect retries do not change context. A terminal assistant drains FOLLOW_UP in its publication transaction and continues with a fresh attempt 1 instead of finishing. `runNext` atomically claims pending NEXT_RUN message targets into a new run intent and publishes their original provisioned IDs. Agent queue suppliers remain outside this stage. Durable abort publication now also triggers process-local cancellation registrations after the abort record commits. `SessionRunOperation` registers `AgentLoopRun.cancel`, and every active tool invocation registers its `CancellationSource`; registration rechecks durable abort to close the check/register race. Cancellation is advisory and accelerates shutdown, while terminal arbitration continues to read the durable abort record. These APIs do not change `AgentHarness 0.84.2`, whose executable run surface is still unpublished.

Compaction is split into deterministic preparation and a summary effect. `ContextCompaction` estimates tokens from the latest valid assistant usage plus trailing-message heuristics, selects only user/assistant/branch-summary cut points, preserves tool-call/result boundaries, carries the previous checkpoint's retained tail forward, and emits a separate turn-prefix request when the cut splits a turn. Read/write/edit tool calls become sorted read-only and modified-file metadata inherited by later checkpoints. `CompactionSummarizer` is the effect boundary; `ModelCompactionSummarizer` implements it through the existing `AgentLoop` and `ModelStream`, using standalone sessions, no tools, upstream summary prompts, thinking-level propagation, and an immutable model output cap. `SessionCompaction` appends the completed result as one immutable compaction entry only after all summary requests settle. `BranchSummarization` finds the abandoned side of a branch through its deepest common ancestor, applies a recent-token budget, excludes tool-result messages, carries file metadata, and can append a branch-summary entry beneath a lane already positioned at the navigation target.

`SessionRecordLogValidator` validates a lane's durable recovery slice without mutation. It rejects multiple open operations, unknown operation references, records after finish, non-consecutive or inconsistent structural attempts, queue activity after abort, invalid cancellations, duplicate/mismatched tool invocations, and provisioned entries whose settled payload differs from intent. `AgentSession.validateRecordLog` composes the required record, entry, and open-operation reads. `HarnessEventBus` supplies the upstream snapshot-first observation primitive independently of the still-unimplemented Harness executor: a watcher is registered before snapshot capture, buffers events until `start`, preserves reentrant emission order while flushing, and unsubscribes without replay.

`AgentSession.transaction` provides a synchronous mutation scope over the existing v4 record model. The in-memory state captures every mutable index before execution, buffers generated mutations, publishes the durable batch while holding the state monitor, and rolls back sequence, tree, records, usage, facts, lanes, labels, and open-operation indexes on any callback, validation, or persistence failure. A transaction view expires when its callback returns and nested transactions are rejected. JSONL keeps the published one-mutation-per-line v4 wire shape: it copies the current file to a sibling temporary file, appends every encoded mutation, forces the staged file, and requires an atomic replacement of the original. Lack of filesystem atomic-move support fails the transaction instead of weakening its contract.

`SessionNavigation` is an executable session-level extension, deliberately separate from the 0.84.2 `AgentHarness` scaffold. Acceptance atomically captures the source leaf, validates current/root/unknown targets and label/summary constraints, enforces the per-lane open-operation gate, and persists a navigation intent with a reserved summary entry id. Summary generation runs outside the transaction against immutable source and target paths. The terminal transaction rereads abort state and then either records an aborted outcome without moving the leaf, or publishes the target move, optional branch-summary entry parented at the target, completed-leaf label, and operation finish together. Effect failure terminates the operation as failed while preserving its source leaf. Thus a crash can expose the accepted pre-terminal operation or the complete navigation result, but no moved-without-summary state.

`SessionNavigation.resume` first validates the lane recovery slice and resumes its single open navigation operation without writing another acceptance record. An unsummarized operation proceeds directly to its terminal transaction. A summarized operation with an unsettled attempt treats that effect as unknown and writes a later numbered attempt before dispatch, preserving usage rows from earlier attempts. Durable abort short-circuits before attempt creation or Provider invocation. Exhausted attempts terminate as failed, and a process-local claim prevents two drivers from dispatching the same loaded operation concurrently. `requestAbort` is idempotent for an open operation. The published record intent does not capture retry policy, so the extension requires `RecoveryOptions.maxAttempts` explicitly; it does not infer the richer policy described by the unpublished register-based interpreter design.

`SessionCompactionOperation` applies the same durable lifecycle to manual, threshold, and overflow compaction. Preparation runs inside the acceptance transaction against the current lane branch, so `NothingToCompact` and an unmet threshold reject with zero writes and no stale leaf/preparation window. Acceptance reserves the checkpoint id in a compaction intent. Each effect dispatch first appends a numbered `COMPACTION` attempt carrying its reason; successful summary usage is recorded before the terminal transaction atomically appends the reserved checkpoint and operation finish. Abort or effect failure leaves the source leaf unchanged. Recovery validates the log, rejects a settled checkpoint under an open operation, preserves earlier usage, checks the caller-supplied reason against durable attempts, and dispatches only a later numbered attempt below the explicit cap. Durable abort prevents any new summary request. Because record-v4 compaction intent stores custom instructions and result id but not settings, reason, context window, or retry policy, recovery requires settings, reason, and `maxAttempts` from the caller rather than inventing them.

`SessionOperationInspector` reconstructs every lane's open operation from validated durable records. It reports operation kind, acceptance timestamp, source leaf, latest structural attempt, and `SUSPENDED` versus durable `ABORTING`. For an open run it also projects every `ToolStarted` whose reserved result entry is absent, preserving source index, call/name/result identity and replay policy. SAFE effects are marked `REPLAY_ALLOWED`; NEVER effects are marked `ADMINISTRATIVE_RESULT_REQUIRED`, directly identifying the `resolveNever` path without probing a lock or dispatching an effect. The projection shrinks as source-ordered results become durable and survives JSONL reopen; it can project the published 0.84.2 `SuspendedOperation` shape with crash reason and empty missing-identity lists. Idle lanes are omitted and corruption propagates instead of yielding a plausible snapshot. Its `lastResult` projection uses one bounded terminal snapshot per lane. Append and replay capture the matching open acceptance, finish record, and lane leaf at the exact finish mutation; transaction rollback restores the prior snapshot, and forks start without it because they do not copy records. Queries are O(1) per lane plus an optional published-entry lookup, independent of record/log length. Later leaf movement and a newer open operation do not change the snapshot. Completed compaction and summarized-navigation publication IDs must resolve to matching entry types; absence is corruption. This remains an in-memory index rebuilt from append-only v4 records on open, not the durable `lane.lastResult` register from the unpublished transaction design.

`SessionOperationEventBus` is a separate Java extension because the published 0.84.2 `HarnessEvent` union contains only run start/end. Navigation and compaction overloads optionally emit `Started` after durable acceptance, `AttemptStarted` after the attempt record, and `Finished` after the terminal transaction. Resume never replays historical start. Pre-acceptance rejection and corruption emit nothing, listener exceptions are passive, and snapshot-first watches buffer through capture and reentrant flush. `SessionToolExecutionEventBus` applies the same watch contract to effect start/completion and durable result publication. A session-shared `SessionRunQueueEventBus` emits `Enqueued`, `Cancelled`, and `Consumed` only after successful transactions; public queue operations and run-internal STEER, FOLLOW_UP, and NEXT_RUN consumption all use that bus. `SessionRunQueue.watch` registers before capturing its durable pending projection, closing the registration window without treating events as replay authority. Lane views from one handle share the queue bus. All of these events are in-process live hints only; a reopened handle starts with a durable snapshot, and reconnect uses queue projection, the inspector, and record log as authority. Session operation/tool/queue watches default to a 1024-event registration buffer and expose an overload for a smaller or larger positive capacity. Before `start`, handles report buffered count, overflow state, and dropped-event count. Overflow clears retained payloads, stops further accumulation, and makes `start` throw `SessionWatchOverflowException`; the failed watch automatically unregisters and the caller must capture a new durable snapshot. This avoids silently presenting a snapshot followed by a gapped event stream. The upstream-facing Harness watch remains behavior-compatible and separate from this bounded session extension.

Both codecs use Jackson's structured tree API. The official `openai-java` SDK is kept as a protocol reference rather than a runtime dependency: its generated Kotlin model layer and OkHttp client do not fit the Vert.x-only transport boundary, and its strict generated types reject several compatible-provider variants handled by upstream pi. Transport certificate verification is enabled by default; `trustAll` exists only for controlled development and self-signed integration tests.

Proxy configuration, WebSocket providers, and additional provider protocols remain future increments.
